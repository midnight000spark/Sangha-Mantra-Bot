## Scope и критерий приёмки

A06 проверяет текущий single-campaign Cloudflare 1.x: человек пишет/редактирует сообщения, нажимает реальные inline-кнопки, работает в личке, наблюдает публикации и реальные права. SC27 разделяет это с будущим B27: multi-campaign, настройка forum topics/General, pause/resume, новые роли и экраны v2 здесь не заявляются. Текущий Worker фильтрует chat ID, а не topic; отдельная закрытая supergroup **без forum** обязательна. Не запускать A06 в теме настоящей группы.

Существующий `scripts/telegram-e2e.py` — bot-to-bot и не закрывает эту приёмку. `maintenance-test-setup.ts`, `test-probes.ts` и другие setup/probe scripts имеют собственные targets, synthetic payloads и/или выполняют deployment; автоматически запускать их по этому плану нельзя. Нужны отдельно проверенный приватный config и разрешённый пошаговый setup ниже. Все параметры из repository `wrangler.jsonc` — fictitious, не проверенные live identities; в шаблоне TEST/production даже одинаковый EXPECTED_BOT_ID, поэтому копирование шаблона не доказывает isolation.

Применяемые labels: `LOCAL_D1_WORKERD`, `HUMAN_NATIVE`, `NATIVE_PROVIDER_CRON`, `NATIVE_TELEGRAM_RETRY`, `CONTROLLED_HTTP_REPLAY`, `CONTROLLED_TEST_FAULT`, `ACCELERATED_NATIVE_REPORT`. У каждого шага отдельный expected/actual и PASS/FAIL/UNKNOWN/NOT_RUN. Общий PASS запрещён при UNKNOWN обязательного шага. Скриншот отсутствия ответа без положительного контроля доставки не доказывает тишину.

## Права, наблюдение и setup после отдельного разрешения

Обозначения: H — обычный участник; A/B — разрешённый private admin; G — владелец TEST группы; O — оператор с ровно нужными TEST CF правами и приватным webhook secret; V — наблюдатель read-only TEST D1. В SQL закреплена campaign `sangha-a06-native-test`; для отдельного accelerated environment оператор создаёт проверенную копию с новым точным ID.

Шаблон единственного будущего read-only вызова (сейчас **не выполнялся**):

```bash
bun node_modules/wrangler/bin/wrangler.js d1 execute DB --remote \
  --env test --config /ABS/PRIVATE/wrangler.a06.json \
  --file docs/A06_TEST_OBSERVATION.sql --json > /ABS/PRIVATE/Q-before.json
```

Перед этим независимо проверить config account/UUID/name/env и фактическое разрешение на remote read. Само наличие `--env test` не защищает от неверного config. Порядок будущего setup: owner approval на заполненную матрицу + SHA/config/window → создать новые ресурсы → migrations0001–0009 с writers/Cron/webhook OFF → проверить schema/ledger → отдельно вне intake создать real marker и сохранить его date/ID → provision identity/campaign/alias/boundary и initial silent=1 по approved receipt → установить secrets → deploy только TEST, проверить config/bindings и 100% version → подключить TEST webhook без drop_pending_updates при закрытых group send permissions и отсутствии pending group intents → A отправляет fresh native `/silent on` в DM → проверить accepted receipt, source watermark/holds → восстановить TEST group send permission, включить Cron. Initial policy silent=1 — setup safeguard, но не замена accepted native ON. Marker не отправляется runtime-ботом как вклад. Сохранить source facts до установки boundary; старые originals из H06 подготовить до enrollment.

После каждого async шага дождаться commit и завершения `waitUntil`/claim по D1 и invocation evidence; допустимый observation timeout 120с или 2 Cron интервала (10мин) для scheduler-driven шага. Timeout = UNKNOWN/FAIL с сохранением состояния, без blind repeat. У notices нет notice_audit таблицы: состояние/claim/source_event_key сверяются с operational_events и invocation records; историю, которой нет, не выдумывать. `runReports().created` на D1 включает trigger changes; authoritative число отчётов — COUNT/ключи daily_reports и report_audit.

Cloud handler C01 и report period C02 — разные evidence.

**Ответ на вопрос о полуночи:** все deterministic boundary/order/error checks выполняются локально без ожидания. Хотя бы один реальный human+provider Cron+held-report/release цикл можно получить C04 за короткое окно, отдельно зафиксировав accelerated label. Полностью заменить C03, сохранить именно native Moscow multi-day поведение и одновременно не ждать нескольких реальных дней нельзя. В таком режиме SC27 длинной native тишины остаётся UNKNOWN/PARTIAL; отдельное owner scope decision может принять сокращённую фазу TEST, но не превратить C04 в C03 PASS. ## Receipt и GO/NO-GO владельца

Шаблон [receipt](A06_TEST_RECEIPT.template.json) требует по каждому ID: действия/время/actor role/source references, expected/actual total+rows+states, D1 before/after JSON hashes, Telegram publication IDs/screenshots, invocation/version references, label/status и причину UNKNOWN. Raw personal payloads/credentials остаются приватными. SHA/config/runtime/migration digests фиксируются до setup и после restart; timestamps включают UTC, timezone и original seconds отдельно от processing milliseconds.

**Подготовка локально GO**, когда три последовательных suite PASS, patch/manifest/hashes воспроизводимы, матрица и шаги доступны review. **Запуск TEST сейчас NO-GO**: реальные identities/права/config/window/owner authorization не заполнены, внешние checks NOT_RUN. Для разрешённого TEST GO дополнительно: подписанные ресурсы и permissions, exact candidate+config digest, TEST-only credentials, planned boundary facts, confirmed native testers+DM, reviewed setup/fault gateway artifacts, evidence storage/retention, STOP owner и часы window. A05 provider PITR остаётся отдельным NOT_RUN gate; он не мешает подготовке/обычному synthetic TEST, но блокирует заявление полного A05/production transition.

Отдельное решение владельца должно явно охватить:

1. Все Telegram/Cloudflare **reads** для проверки identities, permissions, webhook, D1/logs/metrics; согласие human testers и приватные evidence.
2. Создание/настройку отдельного bot, TEST group/participants/privacy/membership, D1 и Worker; secrets upload; migrations/enrollment/identity/boundary TEST writes; exact deploy/redeploy candidate/config.
3. TEST webhook set/change **без drop**, Cron enable/disable, реальные сообщения/edits/callbacks/admin corrections/releases/silent и TEST membership loss/rejoin.
4. Отдельные controlled HTTP replay/probes и временный gateway503 для R01, queue/send pause для H11; bounded window, reviewed artifacts, privacy и rollback/drain. Плана недостаточно для разрешения непроверенного proxy.
5. Выбор C03 полного native календарного окна и/или C04 дополнительного accelerated стенда, ожидаемого evidence уровня; разрешение на TEST restart/revoke и последующее сохранение/teardown ресурсов.
6. Provider TEST PITR point/restore/undo — **самостоятельное** разрешение по A05, не включённое в обычный A06 run. Push/merge/production deploy/cutover/restore/коррекция35 также не входят в A06 и не разрешаются этим результатом.
