# Продолжение после maintenance

В этой публикации сохранены код и регрессии тишины, границ автоматического учёта и читаемой админки. Частные рабочие снапшоты, история реальных накоплений, deployment IDs и эксплуатационные receipts исключены. Подробная модель и ограничения: [MAINTENANCE.md](MAINTENANCE.md).

Перед продолжением проверьте текущий Git HEAD и рабочее дерево, затем используйте проверки именно этого кандидата. Не выдавайте старые результаты за проверку изменённой версии.

```bash
bun install --frozen-lockfile
bun run check
bun run build
bun run backup:drill
```

Cloud-испытания выполняйте в отдельном TEST-боте, группе и D1. При проблеме доставки сверяйте bot identity, Privacy Mode, членство, webhook, очередь и конкретные chat/message IDs. Наличие доступа и успешно выполненный synthetic replay не доказывают получение настоящих сообщений пользователя. Структурная TEST-диагностика помогает отличить недоставку от неподдерживаемого sender-контекста, не сохраняя текст.

Перед production нужны проверенные actual identities, свежая восстановимая копия, согласованная граница вступления бота и независимая live-приёмка нужной версии. Подтвердите текущие CPU/квоты; локальные workerd-тесты и отсутствие metric rows их не заменяют. Публикация кода или PR не означает разрешения развёртывать рабочий сервис.

Порядок: миграция0007 → отдельно проверенный enrollment границы → управляемый переход кода → health/версии/исправления/новые события → доставка и CPU. Короткое окно смешанных версий требует отдельного плана: старый код игнорирует тишину и удержания. Откат на такой код небезопасен; нужен совместимый резервный билд или согласованная остановка без сброса очереди. Данные и существующие overrides не откатывать и не очищать.

Не подключайте TEST webhook к существующему рабочему боту и не публикуйте секретные файлы, SQL dump, базы или логи. При публикации следующих изменений используйте только очищенный репозиторий; исходную частную Git-историю не переносите.
