# Настройка отдельного развёртывания

Вымышленные ID в этой копии согласованы между конфигурацией, защитными проверками и тестами. Это шаблон исходников, а не готовая конфигурация чужого сервиса. Перед cloud-операциями настройте собственные ресурсы и проверьте изменения.

## Изоляция

Используйте отдельные TEST-бота, группу, Worker и D1. Не подключайте тестовый webhook к работающему боту: Telegram поддерживает один webhook на бота. Отключите Privacy Mode через BotFather и добавьте бота в тестовую группу заново. Нужны право отправки сообщений и личный диалог администратора с ботом.

Настройки находятся в `wrangler.jsonc`: аккаунт, UUID D1, bot/chat/admin IDs, campaign ID, timezone, дата начала, цель, максимум за сообщение и время отчёта. В примере стоят намеренно вымышленные значения, включая нулевой account ID и `example-subdomain`.

Некоторые операционные инструменты и production-изоляция дополнительно закрепляют целевые значения в исходниках. Перед собственным развёртыванием согласованно пересмотрите:

- `src/config.ts` — разрешённая production-кампания/чат и запрет TEST D1;
- `scripts/production-ops.ts` — ожидаемые аккаунт, бот, D1, чат и origin;
- `scripts/connect-production.ts` — те же идентификаторы, username бота, старый/новый webhook;
- `scripts/production-tail.ts` — версия Worker для ограниченного сбора метрик;
- соответствующие тесты конфигурации и операционных защит.

Сохраняйте проверки совпадения, не отключайте их ради прохождения установки. Опубликованные тесты подтверждают согласованность примеров, а не пригодность вашей cloud-конфигурации.

## Секреты и подготовка

Настоящие BOT_TOKEN, WEBHOOK_SECRET и BACKUP_KEY_BASE64 не должны попадать в Git, логи, issues или сообщения. Используйте локальные игнорируемые файлы с ограниченными правами и секретные bindings Workers. Не сохраняйте реальные значения в `.dev.vars.example`.

`scripts/prepare-test.sh` и `prepare-test.ts` помогают подготовить отдельного нового TEST-бота. Скрипт отказывается забирать бота с существующим webhook. Прочитайте код перед запуском: он обращается к Telegram и создаёт частные файлы в `.secrets/`. Для live-инструментов требуется собственный проверенный deployment receipt `.secrets/test-deployment.json`; он не включён в публикацию и не создаётся локальными тестами автоматически.

После создания собственной D1 примените миграции в выбранной среде. До запуска Worker отдельно зарегистрируйте идентичность: для TEST таблица `deployment_identity`, для production — `production_deployment_identity`. Значения должны точно совпадать с конфигурацией: environment, database_id, campaign_id, bot_id, source_chat_ids и report_chat_id. `scripts/test-target.ts --sql` генерирует только TEST enrollment; для локальной среды добавьте `--local`.

Не копируйте таблицу идентичности или данные TEST в production. Кампания после инициализации фиксирует timezone, start_day и goal; изменение требует отдельно проверенной миграции.

## Публикация и webhook

Сначала выполните локальные проверки из README. Затем проверьте реальные UUID/имена ресурсов, права бота, секретные bindings и защищённый `/health`. Только после этого переключайте webhook. Сохраняйте очередь: `drop_pending_updates: false`. Рабочие типы updates: message, edited_message, my_chat_member, callback_query.

`bun run deploy:production` намеренно заблокирован. Production-развёртывание выполняйте явной командой Wrangler только после проверки собственной конфигурации. Скрипт `connect-production.ts` также загружает secrets и меняет webhook: это действие, а не read-only диагностика.

## Эксплуатация

- `monitor.ts` проверяет здоровье, членство бота, очередь и свежесть Cron.
- `production-ops.ts check|backup` и `production-maintenance.ts` предназначены для отдельно настроенных production-идентификаторов.
- `install-production-maintenance.ts` устанавливает пользовательские systemd units на машине оператора. Для работы нужны доступная машина, окружение и авторизация. Это не независимое хранилище и не внешний канал тревог.
- Резервные копии и результаты содержат операционные данные: храните вне публичного репозитория. Ключ копий храните отдельно. Регулярно проверяйте восстановление в отдельную базу; не импортируйте пробное восстановление в рабочую D1.
- После восстановления отправка отчётов блокируется до сверки. Неопределённый результат sendMessage не повторяется автоматически: иначе возможен двойной отчёт.
- Реальные webhook, Cron, доставка ежедневного отчёта, CPU и ограничения выбранного Cloudflare-плана требуют отдельных live-проверок. Локальные тесты их не подтверждают.

В публикации оставлен только CI локальных проверок. Scheduled backup/monitor workflows и действующие эксплуатационные receipts исключены.
