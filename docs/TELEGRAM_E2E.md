# Автономная Telegram-приёмка

`scripts/telegram-e2e.py` использует настоящие sendMessage/editMessageText/sendPhoto/sendVideo/getUpdates и отдельные TEST Worker/D1. Настоящие сообщения и ответы наблюдаются через Telegram; итог и outbox сверяются read-only запросами к настоящей TEST D1. Синтетические вклады в D1 не записываются. Начальный enrollment относится только к новой тестовой кампании после реального marker-сообщения.

## Подготовка

Нужны Python 3, Bun с установленными зависимостями проекта, ffmpeg для тестового видео, два отдельных тестовых бота, закрытая supergroup, права администратора обоим ботам, Bot-to-Bot Communication через BotFather и действующая авторизация Wrangler. У отправителя не должно быть чужого webhook или параллельного getUpdates consumer. Проверка видимости реального ответа получателя выполняется до оценки отсутствия предупреждений. Основной Telegram-аккаунт пользователя не нужен.

За пределами checkout и его родительского workspace создайте каталог 0700 и два файла 0600. Пример содержит вымышленные значения:

`credentials.json`:
```json
{"receiver_token":"123456:TEST_TOKEN_PLACEHOLDER","sender_token":"234567:TEST_TOKEN_PLACEHOLDER"}
```

`settings.json`:
```json
{"account_id":"00000000000000000000000000000000","receiver_id":123456,"sender_id":234567,"chat_id":-1001234567890,"chat_title":"testmantra","previous_test_webhook":""}
```

`previous_test_webhook` разрешает перенос только заранее проверенного TEST-бота с конкретного TEST URL. Чужой webhook блокирует setup. Имена ресурсов закреплены: `sangha-mantra-e2e-test`, кампания `sangha-e2e-test`. Existing D1 без собственного receipt не принимается автоматически. Receipt, private config, секреты и результаты сохраняются вне репозитория. Не копируйте их в PR.

```sh
python3 scripts/telegram-e2e.py --setup --private-dir /absolute/private/directory
python3 scripts/telegram-e2e.py --run --private-dir /absolute/private/directory
```

Setup создаёт TEST D1, применяет миграции, проверяет UUID/имя, записывает TEST identity и границу новой кампании, разворачивает отдельный Worker, устанавливает TEST secrets через stdin и меняет только TEST webhook с `drop_pending_updates=false`. В личном Bot-to-Bot диалоге Telegram выдаёт разные message_id отправителю и получателю: для входа используется текст/дата и проверенная пара ботов, для ответа — reply_to_message на стороне наблюдателя. Для групп сохраняется единый исходный message_id.

Повторный run использует исходную сумму как baseline и новые message IDs; run UUID хранится в отдельном результате. Не сбрасывает данные прошлых запусков. Тестовые сообщения оставляет для независимой сверки. Финальное состояние — /silent on. При сбое сохранён частичный результат, успешная приёмка не заявляется; проверьте актуальное состояние /silent перед повтором.

## Ограниченное исключение для бота

По умолчанию сообщения любых ботов отвергаются. Для TEST требуются оба поля `TEST_SENDER_BOT_ID` и `TEST_SENDER_CHAT_ID`. Config отвергает production, неполную пару, собственный bot ID и посторонний чат. Приём разрешён только этому отправителю в этом разрешённом чате, после успешной проверки фактической D1 deployment identity. Пересылки и sender_chat по-прежнему исключены.

Отдельный административный путь стенда — настоящий личный Bot-to-Bot диалог с получателем. Тот же тестовый отправитель должен быть явно включён в `ADMIN_IDS`; только его собственный private chat может управлять кампанией. Групповые команды не становятся административными. Производственный бот по-прежнему требует человека-администратора в личном диалоге. У тестового отправителя нет автоматического цикла ответов.

Только для этого allowlisted TEST отправителя сохраняется нормализованный envelope `TEST_BOT_INPUT` в operational_events. Пересылки, sender_chat и человеческие сообщения туда не попадают. Это позволяет отличить доставку от изменения суммы и повторить полученный envelope для fault injection. Секретов в envelope нет. TEST данные и receipts остаются приватными.

## Что доказывает запуск

Матрицу правильных/неправильных чисел в обоих режимах, реальную доставку предупреждений и личных административных ответов, редактирование собственных сообщений, суммы в D1, сохранение тишины после нового cloud deployment и отсутствие автоматического освобождения удержанных уведомлений после OFF. Команды status/recent/inspect/reports/notices/help, override/release/import идут через Telegram.

Повтор и устаревшая редакция проверяются повторной отправкой захваченного настоящего envelope в защищённый webhook. Это **транспортная fault injection**, а не доказательство того, что Telegram сам повторил update или поменял порядок. Replay не используется вместо первоначальной настоящей доставки.

Bot messages не доказывают поведение обычного человека, нажатия inline-кнопок, права обычного участника, Group Privacy для человека или доставку удалений. Длительную тишину через несколько календарных отчётов, неоднозначную потерю ответа Telegram и гонки отправки проверяют локальные workerd/D1-тесты; живой прогон не должен обозначать их как native Telegram PASS. Отдельно фиксируйте live Cron и CPU, если они действительно наблюдались.

Telegram: [Bot-to-Bot Communication](https://core.telegram.org/bots/features#bot-to-bot-communication), [Bot API](https://core.telegram.org/bots/api). После завершения испытаний перевыпустите переданные в диалоге тестовые токены и обновите только TEST bindings.
