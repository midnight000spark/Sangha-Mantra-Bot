# План перехода после независимого ревью

Этот документ не разрешает production deploy. Публичные ID в wrangler.jsonc и production guards — вымышленные: запуск этого шаблона против production без согласованной конфигурации запрещён. Реальную границу не брать из TEST marker или даты данного прогона.

1. Получить отдельное разрешение владельца. Сверить реальную identity бота/Worker/D1 и текущую версию, сохранить свежую защищённую копию и проверить восстановление. Сверить текущий итог и журнал корректировок, отдельно сообщения 32/38; исторические 38 450 не являются ожидаемым текущим итогом. Не публиковать строки пользователей.
2. По подтверждённым данным установить фактическую границу первого учёта. Если доказательств нет, остановить rollout; не использовать «сейчас». Подготовить точный enrollment SQL и независимую проверку условий first_message_id/original_not_before. Существующие вклады и коррекции остаются неизменны.
3. Подготовить совместимый резервный билд, уже понимающий `campaign_controls`, `publication_hold`, watermarks и intake boundaries. В качестве исходника резервного кандидата можно рассмотреть 6573d24: он уже знает эти ограничения, но возвращает прежнее подавление multi-number warnings. Его реальные production guards/config должны пройти отдельную проверку; это не разрешение на готовый rollback. Проверить резервный билд на копии вместе с кандидатом. Откат на исходный старый Worker опасен: тот отправит удержанные сообщения и может принять старые редакции. Если совместимого билда нет, откат — согласованная временная остановка обработки с сохранением очереди, а не восстановление старой базы.
4. На согласованное короткое окно приостановить **оба** источника запусков старого кода: входящие webhook-запросы и Cron. Использовать временный gateway/совместимый maintenance Worker, возвращающий 503 для webhook, без подтверждения updates. Не делать drop_pending_updates и не менять production-токен. Сохранить прежнее расписание. Дождаться завершения старых invocation/отправок, проверить их результаты. Окно должно укладываться в срок хранения Telegram updates; большой outage требует отдельной сверки полноты.
5. Только когда старый код больше не исполняется, применить аддитивную 0007 и заранее проверенный enrollment. Установить сохранённый /silent on до возобновления. Проверить отсутствие переписывания contributions/overrides/admin_adjustments. Сами миграции не устанавливают производственную границу.
6. Перевести 100% трафика на проверенный кандидат с сохранёнными identity и secrets, исключая смешанную обработку старым кодом. Вернуть webhook-доставку с сохранением очереди и Cron. Контролировать 503/pending updates, heartbeat, новую сумму, старые коррекции, версии, UNCERTAIN и CPU. Не считать отсутствие новых событий доказательством полноты. Сверять реальные message IDs и оригинальные даты.
7. После сверки выключить /silent отдельным решением владельца. Удержания не снимать пачкой. Для каждого отчёта/уведомления проверить Telegram и применить report_sent/notice_sent либо разрешить один повтор с причиной. UNCERTAIN автоматически не повторять. Уже разрешённый перед последней D1-проверкой Telegram-запрос может завершиться после включения тишины.

При проблеме оставить тишину и перейти на проверенный совместимый резервный билд с той же D1. Не удалять миграции, не восстанавливать старый snapshot поверх новых вкладов и не обнулять очереди. Зафиксировать checkpoint и сверить события переходного окна; повторная доставка безопасна, неизвестные пропуски из одного Bot API не восстанавливаются.
